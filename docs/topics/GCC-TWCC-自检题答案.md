## 1. 为什么 TWCC 把计算放在发送端？

你的答案基本正确：

- 接收端不知道发送时间，`send_time`、`pacing_info`、`size` 只有发送端有。
- 发送端有完整发送上下文。
- 反馈紧凑，只传记录，不传计算。

补两点：

1. **跨 SSRC 统一**来自「transport-wide sequence number 由发送端统一分配」，不是「发送端计算」本身带来的。
2. 发送端还能把 BWE 和 **pacer / probe / 编码目标**结合，接收端没有这些信息。

一句话：

> 接收端只负责「记录到达」，发送端负责「结合发送历史做判断」。

## 2. 延迟控制器为什么用 trendline，而不是单次延迟？

你的答案正确：

- 单次延迟受抖动、调度、重传影响大。
- trendline 看的是累积延迟的发展趋势。

补三点：

1. trendline 是对「累积延迟 vs 时间」做**线性回归**，取斜率。
2. 判定不是直接看斜率正负，而是算 `modified_trend` 后和**自适应阈值**比较。
3. 它能比丢包更早发现「队列在变长」，这是延迟控制器的核心价值。

一句话：

> 单次延迟是噪声，趋势才是拥塞信号。

## 3. overuse 为什么要持续 10ms？

代码里不是「一超过阈值就 overuse」，而是：

```cpp
if (time_over_using_ > overusing_time_threshold_ && overuse_counter_ > 1) {
  if (trend >= prev_trend_) {
    hypothesis_ = BandwidthUsage::kBwOverusing;
  }
}
```

其中 `overusing_time_threshold_ = 10ms`。

原因：

1. **过滤瞬时尖刺**：一次突发、一次调度抖动，不应该立刻降码率。
2. **避免震荡**：如果单样本就降，码率会来回抖。
3. **确认趋势仍在上升**：`trend >= prev_trend_`，防止「已经回落」还误判。
4. 10ms 是**最小持续时间**，不是总反应延迟；实际还受反馈间隔影响。

一句话：

> 10ms 是「确认拥塞持续」的最小窗口，不是「等 10ms 才反应」。

## 4. 2% 和 10% 两个丢包阈值分别做什么？

你的答案正确（经典丢包控制器）：

| 丢包率 | 行为 |
|---|---|
| `< 2%` | 增加：`min_bitrate_history × 1.08 + 1kbps` |
| `2% – 10%` | 保持 |
| `> 10%` | 下降：`target × (1 - 0.5 × loss)` |

补三点：

1. `>10%` 的下降不是每个反馈都做，代码里有 `kBweDecreaseInterval + RTT` 的限制。
2. `<2%` 的 8% 是「对 min_bitrate_history 的增加」，不是 AIMD 的 8%/s。
3. 如果启用 `LossBasedBandwidthEstimatorV2`，会走 V2 的估计结果；上面是经典路径。

一句话：

> 低丢包慢慢加，中间不动，高丢包按丢包比例降。

## 5. AIMD 的 0.85 是什么含义？

你的答案基本正确，精确说法是：

```
new = estimated_throughput × 0.85
if new > 5kbps: new -= 5kbps
```

注意：

- 0.85 乘的是**估计吞吐**，不是当前目标码率。
- 减 5kbps 是留一点余量，避免刚好卡在容量边缘。
- 降完进入 `kRcHold`，等队列排空，不是马上再涨。

为什么是 0.85：

> 乘性下降要足够狠，才能把队列排空；但又不能太狠，否则码率掉太多。

一句话：

> 0.85 是「乘性减」的 beta，目标是把发送压到吞吐以下。

## 6. 为什么延迟估计是「上限」而不是直接目标？

因为两个控制器的角色不同：

| 控制器 | 角色 |
|---|---|
| 丢包控制器 | 主目标：根据丢包决定当前目标码率 |
| 延迟控制器 | 上限：防止目标码率超过延迟趋势支持的速率 |

代码里：

```cpp
upper_limit = delay_based_limit_;
upper_limit = min(upper_limit, receiver_limit_);   // 启用时
upper_limit = min(upper_limit, max_bitrate_configured_);
new_bitrate = min(new_bitrate, upper_limit);
```

为什么这样设计：

1. **延迟估计噪声大**：直接拿它当目标会抖。
2. **防止冲进队列**：丢包低时丢包控制器可能想加，但延迟已经变差，上限把它压住。
3. **保守取 min**：延迟估计高时，loss-based 仍可更低；延迟估计低时，强制降。
4. 还有 receiver limit、max configured 两道 cap。

一句话：

> 丢包控制器决定「想发多少」，延迟控制器决定「最多能发多少」。

## 7. probe 在什么时机触发？

你的列表基本正确：

- 初始启动
- overuse 恢复
- 码率骤降（≤0.66）后 5s 内恢复，按原码率 0.85 探测
- ALR 结束
- 周期性 ALR 探测
- 路由/最大分配码率变化 / 网络状态估计高于当前估计

补三点：

1. probe **不是拥塞时的降码率手段**，是「试探更高容量」。
2. 探测失败/没有提升时，不会硬抬目标码率。
3. 探测包按 probe cluster 发，`ProbeBitrateEstimator` 测这组包的吞吐。

一句话：

> 拥塞时降码率，恢复/应用受限结束时才 probe。

## 8. ALR 是什么，为什么 ALR 期间不增加延迟估计？

你的答案部分正确：

> 应用发送小于目标码率，因为实际发送小于链路容量，不会出现延迟队列。

需要修正：

1. ALR 是 **Application Limited Region**：应用/编码器发不满目标码率，链路没有被充分使用。
2. 但「不会出现延迟队列」**太绝对**：突发、pacer 队列、其他流仍可能造成排队。
3. 更关键的原因是**测量不可靠**：
   - 发送量低于目标，延迟估计缺少足够的「激励」和样本。
   - 此时加码没有依据，等应用恢复发送时容易 overshoot。
4. 所以 AIMD 在 ALR 期间不增加；ALR 结束时用 probe 去重新试探容量。

一句话：

> ALR 不是「链路一定空闲」，而是「当前发送量不足以证明可以加码」。

## 9. Pacer 解决什么问题？

你的答案基本正确：

> 解决编码器数据突增，把数据按一定时间均匀发送。

补三点：

1. 降低瞬时排队，避免「突发把队列打满」。
2. 让 BWE 的延迟测量更准：发送间隔可解释，trendline 不容易被突发带偏。
3. probe 时按 probe 速率发；pacer 队列本身也会引入延迟，目标码率过高时 queue 会涨。

一句话：

> Pacer 把「一坨包」变成「按节奏发的包」，让链路和 BWE 都更可控。

## 10. GCC 和 BBR 的区别是什么？

| 维度 | GCC | BBR |
|---|---|---|
| 信号 | 延迟趋势 + 丢包率 | 瓶颈带宽 + 最小 RTT 模型 |
| 控制方式 | 启发式，AIMD + 阈值 | 基于模型的 inflight/cwnd 控制 |
| 对丢包 | 丢包高会降码率 | 不把丢包当拥塞信号（BBRv1） |
| 部署层 | WebRTC 发送端，输出目标码率 | TCP 拥塞控制 |
| 优点 | 面向实时音视频，和 pacer/编码器联动 | 高吞吐、低排队，抗随机丢包 |
| 缺点 | 延迟噪声/丢包误判会影响；参数多 | 可能不公平、依赖模型准确；实现复杂 |

一句话：

> GCC 是「看延迟和丢包的实时启发式」，BBR 是「估计瓶颈带宽和 RTT 的模型控制」。

面试时不要展开 BBR 细节，抓住「信号不同、控制方式不同、部署层不同」即可。
